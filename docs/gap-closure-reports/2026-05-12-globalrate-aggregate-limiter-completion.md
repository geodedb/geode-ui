## The gap

`APIOptions.GlobalRate` / `global_rps` was generated by genapi but never consumed in `RegisterGeneratedAPI` -- there was no cross-route aggregate rate limiter (only per-route token buckets + the per-IP limiter). The genapi `configx.RateLimitConfig` doc comment claimed a global limiter that didn't exist. This was a latent operator footgun: setting `global_rps: 500` expecting a server-wide cap got nothing. It was previously "noted, not ticketed" -- recorded only in geode-ui's `docs/GAP_ANALYSIS.md` / `GAP_ANALYSIS_RESOLVED.md` text + `docs/ARCHITECTURE.md` (which documented the not-wired behavior). No GitLab issue ever existed (`glab issue list --search "GlobalRate" / "global_rps" / "aggregate rate"` → nothing).

## Option chosen -- A: wire it as a real aggregate limiter

Alternatives considered: (B) drop the unused `GlobalRate` option from the generated `APIOptions` / config; (C) leave it and just keep the doc accurate. **Option A** was chosen because the config knob and the `configx.RateLimitConfig` doc comment already promised a server-wide cap -- making that promise true (purely additively, no `APIOptions` signature change) closes the footgun without breaking any consumer, whereas (B) would be a breaking change to every genapi consumer and (C) leaves operators with a knob that silently does nothing.

## Security notes

The aggregate limiter is purely additive and enforced *after* auth/authz (same place as the per-route limiter), so it cannot weaken any existing control -- it only adds a server-wide ceiling that defaults to off (`global_rps: 0` disables it). The 429 reject path reuses the existing envelope / headers / audit / span machinery, so a cross-route reject is observable identically to a per-route reject. No new attack surface; no change to the per-IP limiter or the per-route buckets.
